## 짐작과 실제

| 짐작                      | 실제                                             |
|-------------------------|------------------------------------------------|
| 페이지네이션 E2E 가 통과 중이다     | 남은 테스트 데이터 덕이었다. 데이터를 정리하니 건너뛰었다               |
| 로컬에서 통과하니 CI 도 통과한다     | CI 는 Node 20. jsdom 30 이 Node 22 이상을 요구했다      |
| `Pageable` 만 펼쳐진다       | `CustomUserDetails` 까지 펼쳐져 `password` 가 문서에 나왔다 |
| 계정 잠금은 무차별 대입을 막는다      | 남의 계정을 10분 잠그는 길도 함께 연다                        |
| 테스트를 늘리면 분기 커버리지가 오른다   | 남은 미커버 상위는 Lombok 이 만든 `equals`/`hashCode`     |
| 버튼이 0개니 설정이 먹혔다         | Swagger UI 는 펼쳤을 때만 그 버튼을 그린다. 접히면 항상 0개       |
| Swagger 를 닫는 건 취약점 수정이다 | 엔드포인트는 프론트 번들에 이미 있다. 표면을 줄이는 판단일 뿐            |

## 통과하던 E2E 가 사실은 건너뛰고 있었다

페이지네이션 E2E 는 이렇게 시작했다.

```js
if ((await cards.count()) < PAGE_SIZE) test.skip();
```

워크스페이스가 한 페이지를 넘길 만큼 없으면 건너뛴다. 오래 개발하는 동안 앞선 테스트가
남긴 워크스페이스가 쌓여 있어서, 이 검사는 늘 실행되고 늘 통과했다. **통과 로그만 보면
검사가 돌고 있는지 건너뛰는지 구분되지 않는다.**

데모 데이터를 정리하며 남은 데이터를 줄이자 그때부터 조용히 건너뛰기 시작했다. 검사가
사라진 것을 알아챌 신호가 없었다.

고친 방향은 "데이터가 있으면 검사한다" 가 아니라 **"검사에 필요한 데이터를 검사가 직접
만든다"** 였다.

```js
await seedManyWorkspaces(20);
await page.goto('/dashboard');
await expect(pagination).toBeVisible();
```

교훈: **조건부로 건너뛰는 테스트는 없는 것보다 나쁠 수 있다.** 통과 개수에 들어가 있으니
덮여 있다고 믿게 된다. 전제를 만족시킬 수 없으면 건너뛰지 말고 전제를 만들어야 한다.

<br>

## 로컬에서 통과하니 CI 도 통과할 줄 알았다

`jsdom@30` 을 깔고 프론트 단위 테스트가 로컬에서 전부 통과해 그대로 커밋했다.
CI 는 아래 오류로 죽었다.

```
TypeError: webidl.util.markAsUncloneable is not a function
```

문구가 테스트 내용과 아무 관련이 없어 원인을 짚기 어려웠다. jsdom 30 이 끌고 오는
undici 8 이 Node 22 이상의 API 를 쓰는 것이 원인이었다.

```
로컬        Node 24   통과
CI          Node 20   실패 — 여기가 가장 낮은 쪽이었다
Dockerfile  Node 20   실패했을 자리
```

게다가 Node 20 은 이미 EOL(2026-04-30) 이었다. 급한 불은 jsdom 을 26 으로 내려 껐고,
그다음 CI 두 곳과 `frontend/Dockerfile` 을 Node 22 로 올려 근본을 맞췄다.

마지막으로 같은 사고가 반복되지 않도록 사람이 기억하는 대신 도구가 막게 했다.

```json
"engines": { "node": ">=22.22.0" }
```

`.npmrc` 의 `engine-strict=true` 와 함께 쓰면 낮은 Node 에서 `npm ci` 가 바로 멈춘다.
테스트 실패보다 설치 실패가 낫다. 오류 문구가 원인을 그대로 말해준다.

교훈: **실행 환경이 여러 개면 가장 낮은 쪽에서 확인해야 한다.**

## 전역 스위치가 대상을 고를 거라 봤다

Swagger 에서 `Pageable` 이 객체 하나로 잡혀 `page`·`size`·`sort` 를 넣을 수 없었다.
문서를 뒤져 스위치 하나를 켰다.

```yaml
springdoc:
  default-flat-param-object: true
```

`Pageable` 은 잘 펼쳐졌다. 그런데 `@AuthenticationPrincipal CustomUserDetails` 까지 함께
펼쳐져서 `userId`·`password`·`displayName` 이 **쿼리 파라미터인 것처럼** 문서에 나왔다.
실제로 받는 값이 아니라 문서만의 오해였지만, 인증 객체의 필드가 API 명세에 노출되는 건
그 자체로 잘못된 문서다.

되돌리고 대상을 지정하는 방식으로 바꿨다.

```java
public ResponseEntity<ResponseDto> getTasks(@ParameterObject Pageable pageable, ...)
```

12곳에 붙였다. 전역 한 줄보다 손이 갔지만 다른 곳을 건드리지 않는다.

교훈: **전역 스위치는 대상을 고르지 않는다.** 한 곳을 고치려고 켠 설정이 어디까지
바꾸는지 보고 켜야 한다.

<br>

## 계정 잠금이 방어인 줄만 알았다

로그인 5회 실패 시 10분 잠금을 넣고 무차별 대입 방어가 끝났다고 봤다. 그런데 잠금은
**아무나 걸 수 있다.** 남의 이메일만 알면 아무 비밀번호나 다섯 번 넣어 그 계정을 10분간
못 쓰게 만들 수 있다. 사용자 검색과 워크스페이스 멤버 목록이 있으니 대상 이메일을
알아내기도 어렵지 않다.

먼저 눈에 띈 것은 더 단순한 결함이었다. 로그인 실패 처리가 모든 `BusinessException` 을
한 덩어리로 잡아 실패 횟수를 올리고 있었다. **없는 이메일로도 잠금 카운트가 올라갔다는
뜻이다.** 응답 enum 을 보고 갈라서 막았다.

```java
// 비밀번호가 틀린 경우에만 실패 횟수를 올린다.
// 없는 이메일까지 세면 남의 계정을 잠글 수 있다
if (e.getResponse() != INVALID_PASSWORD) {
    return ResponseEntity.status(NOT_FOUND).body(new ResponseDto(EMAIL_NOT_FOUND));
}
int failures = refreshTokenService.incrementLoginFailure(email);
```

하지만 **실재하는 계정에 대한 잠금 공격은 그대로 남는다.** 이건 구현 실수가 아니라
계정 잠금 방식 자체의 성질이다. 강하게 걸면 서비스 거부에, 약하게 걸면 비밀번호 추측에
취약해진다. 지연 증가·CAPTCHA·IP 단위 제한을 얹어야 균형이 잡힌다.

현재는 포트폴리오 수준에서 10분 잠금을 감수한다. 감수한다는 말을 문서에 적어두는 것까지가
대응이라고 본다.

교훈: **방어 수단은 그 자체가 새 공격 표면이 될 수 있다.** "무엇을 막는가" 만큼
"이걸 누가 발동시킬 수 있는가" 를 봐야 한다.

## 커버리지는 테스트를 늘리면 오를 줄 알았다

테스트를 71개에서 301개로 늘리는 동안 수치는 이렇게 움직였다.

```
분기   14.0%  →  33.5%
라인   49.1%  →  72.8%
```

라인은 잘 따라왔는데 분기는 더디게 올랐다. 남은 미커버 분기를 열어보니 상위가
`LoginResponseDto` 62개, `InviteResponseDto` 53개 같은 DTO 들이었다. Lombok 이 만든
`equals`/`hashCode` 의 null 검사·타입 검사 분기다. 사람이 쓴 적 없는 코드이고,
채워도 무엇도 검증하지 못한다.

숫자를 올리려면 여기를 덮는 게 가장 싸다. 그래서 덮지 않기로 했다. **분기 커버리지는
목표가 아니라 어디를 안 보고 있는지 알려주는 지표로만 썼다.**

대신 테스트가 실제로 회귀를 잡는지는 따로 확인했다. 프로덕션 코드를 일부러 깨뜨리고
테스트가 빨간불이 되는지 본 뒤 되돌리는 방식으로 네 번 돌렸다. 예를 들어 unwrap
인터셉터에서 `statusCode` 검사를 빼자 재발급 후 재시도 경로가 두 번 unwrap 되면서
테스트가 잡아냈다.

## 대조군 없이 센 0

API 문서에서 Try it out 을 막을 수 있는지 보려고 설정을 넣었다.

```yaml
springdoc:
  swagger-ui:
    supported-submit-methods: []
```

브라우저에서 `button.try-out__btn` 개수를 세어 0개가 나오자 제한이 먹혔다고 봤다.
실제로는 Swagger UI 가 **항목을 펼쳤을 때만** 그 버튼을 그린다. 접힌 상태에서는 설정을
넣든 안 넣든 항상 0개다. 나중에 항목을 펼쳐 다시 세고서야 알았다. 설정이 정말 먹혔는지는
끝내 확인하지 못했다.

결국 이 기능은 되돌렸다. 애초에 문서를 닫는 것을 취약점 수정처럼 다루고 있었는데,
엔드포인트 목록은 프론트 번들에 이미 들어 있어 감춰지지 않는다. 공격 표면을 줄이는
판단이지 구멍을 막는 일이 아니었다. 포트폴리오 용도에는 열어두는 쪽이 맞다고 보고
`SWAGGER_ENABLED` 플래그만 남겼다.

교훈: **0을 근거로 부재를 주장할 때는 1이 나오는 조건을 먼저 만들어봐야 한다.**
대조군 없이 센 0은 아무것도 증명하지 못한다.

<br>

## 다음에 지킬 것

- 조건부 `skip` 은 쓰지 말고, 전제를 테스트가 직접 만든다
- 의존성을 올릴 때 실행 환경 중 **가장 낮은 버전**에서 확인한다
- 전역 설정을 켜기 전에 그것이 어디까지 바꾸는지 본다
- 방어 수단을 넣을 때 "이걸 누가 발동시킬 수 있는가" 를 함께 본다
- 커버리지 수치는 목표가 아니라 사각지대를 찾는 데만 쓴다
- 0을 근거로 부재를 주장하기 전에, 1이 나오는 조건을 만들어 대조한다

겪은 장애와 버그는 [문제 해결](problem-solving.md) 에 따로 있다.
